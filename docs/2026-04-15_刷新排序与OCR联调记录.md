## 已确认问题

### 1. 刷新后聊天内容乱序

- 现象：
  - 刷新页面后，提问卡片、思考过程、报告卡片、AI 文本的前后顺序和刷新前不一致。
- 根因：
  - 历史恢复同时依赖 `/messages` 与 `state` 补造消息，导致聊天区出现双写。
  - `status / plan / guide / inquiry` 等卡片在历史恢复时会被前端再次插入或错误保留。
  - 某些卡片在运行时先由实时事件插入，刷新后又按历史流重建，顺序来源不唯一。
- 已做修复：
  - 聊天恢复改为只认正式消息流。
  - `processStateUpdate(..., { isHistoryRestore: true })` 不再往聊天区补消息。
  - 修复 `status / plan / guide` 的消息正式化与字段映射问题。
  - 修复重复 `report_ready` 发射导致的报告卡堆叠。
  - 增加 `cookie` 鉴权兜底，避免刷新后掉登录态影响恢复链路。
- 当前状态：
  - 需要在“完整跑通到 guide 后再刷新”场景下继续复验。

### 1.1 已定位到的后端根因：resume 回执落盘顺序错误

- 现象：
  - 用户提交补充问卷后，实时页面里会先看到 `已提交问卷` 回执；
  - 但刷新后，回执会跑到 assistant 的 `reasoning / tool / report` 后面，看起来像“报告卡和思考过程全堆在一起，旧提问卡片反而掉到下面”。
- 直接证据：
  - 真实会话 `47d13baa-9528-4784-a6ba-f3508c52b9be` 的 `/messages` 返回里，修复前存在以下顺序：
    - `182000 | assistant | reasoning_event`
    - `182001 | assistant | tool_event`
    - `182002 | assistant | reasoning_event`
    - `182003 | user | inquiry_receipt`
    - `182004 | assistant | interrupt_inquiry`
  - 这说明不是前端单纯渲染错，而是后端持久化消息流本身就把 `inquiry_receipt` 写到了 process events 后面。
- 根因：
  - `/Users/ant/Crushe/模型策略/agent_impl/api/conversation_persist.py`
  - `persist_turn_messages()` 原逻辑先写 `process_events`，再写 `inquiry_receipt`。
  - 对 `resume` 场景来说，`inquiry_receipt` 实际上就是这一轮唯一稳定的“用户消息”，被写晚之后，刷新时前端按 `turn_seq + part_index` 恢复就一定乱序。
- 已做修复：
  - 调整消息持久化顺序：
    - `user/inquiry_receipt -> reasoning/tool/report -> pending_responses -> assessment -> interrupt`
  - 新增单元测试覆盖 `resume` 场景：
    - `test_resume_inquiry_receipt_precedes_process_events`
  - 测试结果：
    - `python3 -m pytest /Users/ant/Crushe/模型策略/agent_impl/tests/test_conversation_persistence.py -q`
    - `21 passed`
- 当前状态：
  - 代码修复已完成并已重启 FastAPI。
  - 已跑出新的真实 turn `183`，消息顺序为：
    - `183000 | user | inquiry_receipt`
    - `183001 | assistant | reasoning_event`
    - `183002 | assistant | tool_event`
    - `183003 | assistant | reasoning_event`
    - `183005 | assistant | system_task (status)`
    - `183008 | assistant | system_task (plan)`
  - 这说明新写入的正式消息流顺序已经符合预期，后端根因修复生效。

  - 主流程中的 MAS 判定拿不到足够截图信息时，会继续追加 inquiry，无法自然进入 `status / plan / guide`。
- 当前状态：
  - 这是独立于“刷新排序”的外部依赖问题，已记录为本轮关键阻塞。
  - 本轮测试中通过“前端已有 OCR 文本跳过上传”路径将链路继续向前推进，用于隔离排序问题。
- 后续建议：
  - 增加 OCR 服务降级策略。
  - 当截图已上传但 OCR 失败时，不要只写“截图解析失败”，而应携带最小可用元信息继续推进，或明确回退到人工补录对话文本的稳态交互。
